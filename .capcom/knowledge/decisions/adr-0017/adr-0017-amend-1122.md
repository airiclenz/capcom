---
title: "ADR 0017 amendment of 2026-11-22: the lock record names the holder process, whose writes stay silent and renew the heartbeat, and another session's warning says to ask the user"
---

Amended 2026-11-22: the lock record names the holder process, and a write made under it is the
holder's. The decision silenced only a write of the Issue whose id is the lock's purpose, so a
holder that filed a child Issue, added a dependency or wrote a Note was warned about its own lock,
and a warning ending "if it is yours, carry on" taught every session, the holder and another alike,
to read past it.

**The holder process.** `capcom lock acquire` and `capcom start` record the holder process in the
lock record: the nearest ancestor of capcom that is not a shell or a wrapper command (`sh`, `bash`,
`env`, `timeout` and the like), by PID and start stamp, so a reused PID never matches. That is the
agent harness the session runs in, which outlives the fresh shell an orchestrator spawns for each
tool call and is an ancestor of every sub-agent it starts. A resume replaces it with the resuming
caller's, and a touch keeps it. A caller whose process ancestry holds that PID with that start
stamp is the holder; a kept token file is not identity, since any session naming the purpose can
read it (ADR 0016).

**The holder's writes are silent and renew the heartbeat.** A write of any Issue or Note made
under the holder process adds no lock warning, whatever it targets, and refreshes the lock's
heartbeat, so a session that keeps writing never goes stale. A renewal that fails warns
`<record>: the lock's heartbeat was not renewed: <why>`, and the write stands. A renewal that finds
the lock taken over since is judged against the new holder's lock as any other caller's write; one
that finds the lock freed is silent. `capcom prime` run under the holder process says
`this worktree: held by this session (<purpose>)`.

**Every other caller keeps the purpose rule.** A write made outside the holder process still stays
silent when every Issue it writes is the one whose id is the lock's purpose; any other write warns.
A record that names no holder process, written by an older capcom or by an acquire whose ancestry
could not be read, warns as the decision says.

**The new warning words.** The warning still names the holder, the purpose and the heartbeat age as
`locked` does, and now ends with what to do: `; another session holds this worktree: the write
landed, ask the user before writing more`, and for a stale lock `; another session's stale lock
holds this worktree: the write landed, ask the user before writing more or taking it over`. Only a
caller outside the holder process sees it, so it no longer asks the reader to judge whether the
lock is its own. In text output every warning line prints before the command's result; `--json`
and `--kv` are unchanged.

**Reading the lock still creates nothing.** The check reads the record without the guard file; only
the holder's renewal takes the guard, as `lock touch` does.

**What it does not tell apart.** Callers that share their nearest non-shell ancestor, such as two
shells in panes of one tmux server, are one holder to capcom.
