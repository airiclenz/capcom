---
title: "ADR 0016 amendment of 2026-11-22: touch, release and check need no --token in the holder process, which uses the kept token matching the record"
---

Amended 2026-11-22: `capcom lock touch`, `lock release` and `lock check` need no `--token` in the
holder process. The decision let acquire and start resume from the token file, while touch,
release and check still took `--token`, so a session that no longer carried the token in its
context had to run the acquire again only to read it back.

**Without `--token` in the holder process.** touch, release and check without `--token` read the
lock record once. When it names a holder process the caller descends from (ADR 0017 and its
amendment of 2026-11-22), they take the token kept in the token file whose token matches that
record and act as they would with `--token`; touch and check print it on their token line. The
holder check and the token come from the same read, so a lock taken over between them is never
acted on with the new holder's token.

**Everyone else as before.** A caller outside the holder process, or a holder with no kept token
matching the record, is a non-holder: touch and release fail `locked` with exit code 3 on a held
lock, their hint naming `capcom lock status; pass --token <token> if the lock is yours`, and check
exits 3. `--token` still works from any process; it is the way for a script, a hook or any process
that does not descend from the holder.

**Why the token file is used but is not identity.** Any session that names the purpose can read a
token file (the decision), so the file alone never says who holds the lock. The holder process
says that, and the token file then supplies the token that acts for it; the Lock token still
decides every change to the lock.

**Touch is rarely needed.** Every Issue or Note write in the holder process renews the heartbeat
(ADR 0017 amendment of 2026-11-22), so `lock touch` is needed only when work outlasts the lock TTL
without a capcom write.
