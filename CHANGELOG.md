# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

- Reading an issue or Note file no longer follows a symlink, or hangs on a named pipe, that replaced the file between capcom's check of it and its open: such a file is refused as not a regular file, like one that was a symlink or pipe from the start.
- A symlinked `AGENTS.md` keeps its link only within the working tree: `capcom agents` and the automatic Managed-block refresh write the block to the file the link points to only when that file lies inside the working tree (`AGENTS.md -> CLAUDE.md` keeps working). An `AGENTS.md` that links outside it (for example to `~/.bashrc`) is never read or written: `capcom agents` fails with `AGENTS.md: links to <target>, outside the working tree; the capcom block is not read or written`, and `capcom check`, `capcom agents --check` and Note writes treat it as having no block. This supersedes the earlier entry that kept a symlinked `AGENTS.md` a link with no such limit.
- `AGENTS.md` is now read through the same guarded reader as the store's files: a named pipe, a directory, or a file larger than 1 MiB in its place (or behind an in-tree link) no longer hangs or exhausts memory in `capcom prime`, `check`, `agents` and Note writes. `capcom agents` and `capcom agents --check` fail with `AGENTS.md: not a regular file` or `AGENTS.md: file is larger than 1 MiB`, `capcom check` reports it as an `agents-block` problem, `capcom prime` counts it in its check line, and a Note write warns that the block was not refreshed. A missing `AGENTS.md`, or one whose link dangles, still reads as having no block.
- `.capcom/config.yaml` is now read through the same guarded reader as the store's other files: a symlink, a named pipe, a directory or a file larger than 1 MiB in its place no longer hangs a command, exhausts memory or gets another file parsed. Every command fails with `.capcom/config.yaml: not a regular file` or `.capcom/config.yaml: file is larger than 1 MiB` (`capcom prime` reports it as a `warning: store:` line). A symlinked `config.yaml` is refused like any other non-regular entry; a missing one still means the default configuration.
- A `path#symbol` Ref whose file is a named pipe or another non-regular entry no longer hangs `prime`, `check` or `know verify`, and one whose file is larger than 1 MiB is no longer read into memory; each is now reported as a Ref that does not resolve.
- The Elsewhere scan behind `list`, `ready`, `show` and `prime` no longer reads another branch's copy of a modified issue file when it is larger than 1 MiB: that file gets no Elsewhere entry and one warning, `elsewhere: branch <branch>: <path>: file is larger than 1 MiB`. A fetched branch that commits a huge issue file can no longer make these commands run out of memory.
- Text output now writes control characters from issue and note files (escape sequences, BEL, CR, DEL, C1 controls and invalid UTF-8) as visible `\xHH` escapes, so a hostile title or body can no longer clear the screen, set the window title or write to the clipboard. `--json` and `--kv` output is unchanged.
- `capcom show` and `capcom know show` now print every field, the body and the etag from one read of the file, in text, `--json` and `--kv`, so `--if-match` with the printed etag always checks against the content shown. Before, a file rewritten at the same size and modification time could print the indexed old title and body beside the new file's etag. A file that no longer parses now fails as invalid at its file and line.
- `capcom dep rm` and `capcom related rm` remove a dangling entry by its text even when that text is a prefix of one or more live issue ids: before, such an entry resolved to the issue it prefixed (removing a valid entry instead, failing `not_found`, or failing as ambiguous), and only a hand edit cleared it. An argument that is exactly an issue's id or alias behaves as before.
- An issue or Note frontmatter, or `config.yaml`, holding a second YAML document (after a `---` line inside it) now fails with `only one YAML document is allowed` at that line, and content after a `...` line fails as invalid YAML; before, everything past the first document was silently ignored, unchecked. `capcom check` reports both. A store raising its format (as `related add` does) on a `config.yaml` that opens with a `---` line now writes `format:` inside that document instead of above it, where it made the file two documents.
- Fixed: an alias of an issue or Note file with problems (invalid fields, or frontmatter that does not parse) no longer falls through to prefix matching, where a command could act on a different node. The alias now fails as the file's id already did: `id "<arg>" not found: <file> is invalid`. The index rebuilds itself once to record these names.
- A command argument that names a file the index leaves out at walk time (a symlinked or named-pipe node file, a node file over 1 MiB, or any node file under a directory left out, by its id or an alias) now fails as not found naming that file, instead of resolving to another issue or Note by prefix.
- `capcom create --id`, a renaming `capcom mv` and a renaming `capcom know mv` now refuse an id that a file left out for a repeated id is named for or lists as an alias, with `id "<id>" is already taken by this file, left out for the duplicate id "<dup>"` (or `an alias of this file`), naming that file; a left-out file that does not parse but still lists the id in its raw `aliases:` line refuses it too. This supersedes "An alias only a left-out file lists is unaffected": create and mv now refuse such an alias.
- **Fixed:** when two node files share an id, capcom no longer keeps the first and quietly lets the other file's children join it, so a move can no longer re-parent them. Every file of the id is left out, and so is every node below a directory beside one of them; `capcom check` reports each such directory as `directory left out: its node file <id>.md has a duplicate id`. Naming a node below a repeated id (by id, alias or prefix) fails with the duplicate problem naming both files, and `capcom create --id` for such a node's id is refused as taken by a file `inside the orphan directory` instead of `already taken by issue <id>`. `rm` is still refused while a left-out file depends on the issue, and `check` reports no missing dependency, related or superseded-by entry for a name a left-out file holds. The AGENTS.md Managed block leaves out any top-level Note whose file a load problem names (a duplicate id or alias, an invalid or repeated alias).
- **Fixed:** the commands that read the index (`show`, `close`, `update` and the listings) now leave out every node below a directory beside a file of a repeated id, as `mv`, `rm` and `create --parent` already did. Naming such a node by id, alias or a prefix only it matches fails with the duplicate problem naming both files of the repeated id; a prefix it shares with another id stays ambiguous. Each such directory is warned about as `directory left out: its node file <id>.md has a duplicate id`.
- `capcom mv`, `capcom know mv`, `capcom rm` and `capcom know rm` no longer overwrite another node's file that changed after the command read it: the command fails naming that file (`changed since it was read`) and takes back the rewrites it already made. A rollback no longer writes over a file changed since the command rewrote it; it leaves the file as it is and names it after `rolling back:`.
- `capcom mv`, `capcom rm`, `capcom know mv`, `capcom know rm` and `capcom fmt` no longer overwrite a file that changed while they ran: when a file they rewrite changes between their read and their write, they fail with a `conflict` at that file, `changed since this command read it; run the command again`, keep its new bytes, and (mv and rm) take back what they had already changed.
- `capcom mv`, `capcom rm`, `capcom know mv` and `capcom know rm` no longer bring back a file another session moved or removed while they ran: a rewrite of a file that is gone by the time it is written, or a re-parent below a node whose file was removed meanwhile, fails the command and leaves the tree as it was, instead of recreating the file or the parent's children directory.
- Commands that change an existing Issue or Note (`capcom update`, `capcom know update` and the other editing commands) and `capcom fmt` no longer bring back a file another session moved or removed while they ran: the write fails at that file and creates nothing. `capcom create` and `capcom know add` below a parent whose file was removed meanwhile fail at the parent's file instead of recreating its children directory with no node file.
- `capcom mv` and `capcom know mv` no longer overwrite a file that another session creates at the new path while the move runs: the move fails naming that path and leaves both files as they were. On a file system without hard links the move works as before.
- `elsewhere.days: 0` now turns the Elsewhere scan off: capcom runs no git command for it and reports nothing, even for a branch whose last commit is dated in the future.
- When git fails outright while resolving HEAD for the Elsewhere scan (for example a broken repository), capcom now reports the git error as a "resolve HEAD:" warning instead of treating HEAD as having no commit yet.
- Listing, searching and resolving issues or Notes (`list`, `ready`, `search`, `show`, `know tree`, `know search`, ...) no longer fail with `id "x" not found`, or mix two versions of one issue, when another capcom command refreshes the index at the same moment: each query now reads all its rows from one consistent snapshot of the index.
- Commands that read the issue or Knowledge tree, and the index refresh, no longer fail with `no such file or directory` when another command moves or removes a child directory while the tree is being read: that directory is now read as empty and every other issue or Note still comes back.
- `capcom log` and `reopen` no longer write a Log entry into a fenced code block that quotes a `## Log` heading above an issue's real Log section, and the git merge driver now merges that real Log entry by entry instead of falling back to a whole-file conflict. The Log opens at the first `## Log` line outside a fenced code block and ends at the next level-one or level-two heading outside one; a fence that is never closed hides nothing.
- `capcom mv` and `capcom know mv` no longer undo a finished move when they cannot remove the old parent's directory that the move left empty: the move stays, and the empty directory is left in place.
- `capcom mv` and `capcom know mv` now warn `<dir>: <reason>; the empty directory was not removed` when the move empties the old parent's directory and cannot remove it, as `rm` and `know rm` do; the move still succeeds.
- `go run ./cmd/release publish vX.Y.Z` no longer moves the Homebrew tap or the Scoop bucket back onto an older release: a formula or manifest that already pins a newer version reads done (`formula pins newer X.Y.Z`, `manifest pins newer X.Y.Z`) and is left alone, and `smoke` skips its `brew upgrade` check when the version is not the latest release.
- `go run ./cmd/release publish vX.Y.Z` no longer treats a draft GitHub release, left by an interrupted `gh release create`, as done: `status` and `publish` report it pending (`release vX.Y.Z is a draft ...`), and `publish` uploads any assets it lacks and then publishes the draft (`gh release edit --draft=false --latest`) before the channel steps point at its downloads.
- `go run ./cmd/release publish vX.Y.Z` now pushes the exact commit the release gate cleared (`git push origin <sha>:refs/heads/main`) and reads `VERSION` and checks the tag's bump commit at that commit, rather than whatever the symbolic `HEAD` is by then; when `HEAD` resolves to another commit before the push it refuses with `HEAD moved from <short> to <short> after the gate cleared it: run publish again` and pushes nothing.
- `go run ./cmd/release publish vX.Y.Z` no longer skips the release gate entirely once the version's tag is on origin: while the GitHub release is not done it checks the gate's CI half over the tag, refusing unless `ci.yml` has a successful run for the tag's commit (with its trailing `CHANGELOG.md`/`VERSION`-only commits peeled off) or a peeled commit `origin/main` contains, and its gate row reads `CI only, the tag is on origin: cleared|BLOCKED at <short>`. The working tree, `HEAD` and `VERSION` at `HEAD` are still not consulted then, and once the release is done the gate is not consulted at all.
- `go run ./cmd/release publish vX.Y.Z` resuming a half-uploaded GitHub release no longer uploads assets the release does not match: with `SHA256SUMS` on the release, every archive, uploaded or about to be, must hash to the published value; without it, every archive already uploaded is downloaded and must hash to the rebuilt one before the rebuilt `SHA256SUMS` goes up beside it. A mismatch refuses before any upload, naming each archive and the `gh release delete-asset <tag> <name>` way out.
- The tag-on-version-bump workflow no longer passes over a VERSION it refuses to tag: a bump that is not a bare `X.Y.Z` (a leading `v` included) still lets every valid bump in the push be tagged, then fails the job. When the push's `before` commit is unusable (a new branch or a rewritten history), it now scans from the newest release tag reachable from the pushed head, so a bump buried under later commits is still tagged. `go run ./cmd/release publish` and `dist` now refuse a VERSION with a leading `v`, naming the VERSION file, instead of accepting it.
- `capcom init` (with or without `--merge-driver`, `--claude-hooks` or `--codex-hooks`) on an existing store that has no `.capcom/config.yaml` now writes the config template with the `format:` line left as the comment `# format: 1`, so the store stays at format 1 and releases that read only format 1 can still read it. A store `init` creates still gets `format: 3`.
- `capcom check` reports a `related` key in an issue file as `format-too-old`, at its line, when the store declares a format below 2; earlier it passed although every format-1 binary rejects the key.
- `capcom mv` no longer leaves a repeated entry when an issue is renamed to an id another issue's `deps` or `related` already names: `deps: [x, y]` renamed from `x` to `y` becomes `[y]`, not `[y, y]`. `capcom know mv <note> --id <new>` on a Note whose `superseded-by` already names `<new>` drops that entry, so the Note no longer names itself.
- `capcom know rm` now reports the Notes whose `superseded-by` entries it dropped: `--json` data carries `superseded_by_dropped` (always present, `[]` when none), and the text output adds a `superseded_by_dropped: [...]` line after `path:` when the list is not empty.
- `capcom close` no longer overwrites an issue another session closed after the command looked it up: it re-checks the issue on the file as read for the write and reports it `already_closed` (text line, `--json` outcome, `--kv` STATUS), keeping that file's `closed:` and `reason:` and announcing no `now ready:` for it.
- `go run ./cmd/release status` and `publish` now find an open winget pull request the signed-in `gh` account just opened in `microsoft/winget-pkgs`, read through `gh api graphql` beside the `gh pr list --search` listing, so a rerun right after a submission reads the winget step done instead of submitting a duplicate pull request while GitHub search has not indexed it yet.

## [0.5.0] - 2026-10-12

- `capcom close` now ends its text output with a `now ready: <id>, <id>` line naming the todo issues the close made Ready (no line when there are none; issues hidden by `ready.hide` are left out). Each `--json` item carries `now_ready`, the ids that argument's close readied given the arguments closed before it, each id reported once across the command and `[]` when there are none. `--kv` output is unchanged.
- `capcom ready` now breaks a priority tie in favour of the issue that unblocks more, before tree order: a Ready issue whose close alone (as done) would make other todo issues Ready ends its line with `  -- unblocks N`, and its `--json` item carries `unblocks`, those issues' ids (left out when there are none; issues hidden by `ready.hide` are not counted). Not-ready lines under `--all` keep their order and gain no suffix. `capcom prime` lists its Ready issues in the same order, with its line format unchanged.
- `capcom show` now tells whether an issue is ready and who waits on it: an issue in the todo category gets a `ready: yes` or `ready: no (<reasons>)` line right after `category:`, the reasons worded as `ready --all` words them, and an issue others depend on gets a `dependents: [<id>, ...]` line right after `deps:`. Its `--json` items gain `ready` (left out outside the todo category), `blocking` (as `ready` reports it) and `dependents` (always present, empty when none); `--kv` output is unchanged.
- `capcom show` on an issue with direct children prints `children: <closed>/<total> closed` right after `dependents:` (or `deps:`), counting done and dropped children as closed; a leaf gets no line. Its `--json` items gain `children` (`{"total": N, "closed": N}`), left out for an issue without children; `--kv` output is unchanged.
- `capcom create --dep <id|alias|prefix>` (repeatable, comma-separated allowed) files a new issue with its dependencies in one command: each is stored as its canonical id, once, in the order given. A dependency that names no issue fails the create with the error `dep add` gives, and no file is written.
- `capcom create` without a body, or with only whitespace, still writes the issue but warns `<id> has no body: state what, why and a "## Acceptance" section with capcom update <id> --body-append-file <file>`, in text after the `warning:` label and in the JSON `warnings` list.
- `capcom know tree --depth N` now shows where the depth cut the outline: under each Note whose children were left out it prints one line, indented one level deeper, `... <n> more (--depth <d>)`, where `n` counts the Note's direct children (retired ones left out unless `--retired`) and `d` is the depth that would show them. Its `--json` items gain `more`, that count (left out when 0); the output is unchanged when nothing is cut.
- `capcom dep list <id> --depth N` prints the deps and dependents sections as indented trees N levels deep (0 prints every level). An issue already printed in a section prints again as `<id>  (see above)`, and a cut branch ends in `... <n> more (--depth <d>)`. Without `--depth` the output is unchanged. JSON items gain `depth` and `via`.
- `capcom list --tree` prints the issue hierarchy as an outline, `id  status  P<n>  title` indented two spaces per level, and ends each parent's line with `  (<closed>/<total> closed)`. Without `--all`, closed issues and their subtrees are left out, but they still count in their parent's progress. `--parent <id>` prints that issue first, then its subtree. `--depth N` limits the levels (0, the default, prints them all), and a cut issue gets a `... <n> more (--depth <d>)` line. A row filter (`--status`, `--label`, `--limit`, ...) with `--tree`, or `--depth` without it, is a usage error. Its `--json` items gain `depth`.
- `capcom dep graph [<id>]` prints the dependencies as a Mermaid flowchart (`flowchart LR`, one node `<id> (<status>)` per issue, edges from each dependency to its dependent): every issue that is not closed, or with an id that issue and its transitive deps and dependents. `--all` adds closed issues; `--json` gives the nodes and edges.
- `capcom know tree` leaves out Notes labelled `background`, with everything below them, in text and
  JSON; `--background` brings them back. A Note named as the start is printed even when it is
  background, and hidden Notes are not counted in the `... <n> more` hints. The capcom block of
  AGENTS.md skips background top-level Notes as it skips retired ones. `know show` and
  `know search` are unchanged.
- The Managed block that `capcom agents` writes into `AGENTS.md` now lists the dependency commands (`create --dep`, `dep add`, `dep list`, `list --tree --depth 2`), says that `show` prints what blocks an issue and `close` names the issues it made ready, states what an issue's body holds (what is wrong or wanted, why, and an `## Acceptance` section; the how and the order belong in a plan), and maps where issues and Notes live under `.capcom/`. An existing block reads as out of date after upgrading: run `capcom agents` once to refresh it (`capcom check` and `capcom agents --check` report it until you do).
- A name that one issue or Note file claims (as its id or an alias) and that a file left out for a repeated id also lists as an alias is now a duplicate: commands refuse it as they refuse any duplicated name, and `capcom check` reports it as `duplicate`. Two such left-out files listing the same alias are a duplicate too. `capcom check` now also reads a file left out for a repeated id, so it reports that file's frontmatter parse failures and conflict markers. An alias only a left-out file lists is unaffected.

## [0.4.0] - 2026-10-12

- The README now has a Non-goals section naming what capcom will not add (a server, multi-writer mode, hosting, a daemon, background sync, notifications) and why, and a FAQ entry with a minimal GitHub Actions workflow that runs `capcom check` and `capcom fmt --check`.
- `docs/format.md` describes an optional `post-merge` git hook that runs `capcom check` after every merge, and when git does not run it.
- New `CONTRIBUTING.md` (build, tests, conventions, changelog and release rules) and `SECURITY.md` (supported versions; report vulnerabilities through GitHub's private vulnerability reporting).
- An entry under `.capcom/issues/` or `.capcom/knowledge/` that is not a regular file (a symlink, a named pipe, a device) is no longer read through: every command leaves it out with a `not a regular file` warning, and a node file larger than 1 MiB is left out with a `file is larger than 1 MiB` warning, so a FIFO or a link to `/dev/zero` can no longer hang or exhaust a command. `capcom check` reports both as code `not-regular` (index warning kind `not-regular`), and a directory beside such a node file is left out with it (`directory left out: its node file <name>.md is not a regular file`).
- `capcom` index refreshes no longer read a symlink, named pipe or device named like an issue or Note file, and no longer fail or hang on one: each is left out with a `not a regular file` warning (kind `not-regular`), and a node file larger than 1 MiB is left out with a `file is larger than 1 MiB` warning, including one that changes between the walk and the read.
- `capcom check`, `update`, `show`, `close` and `fmt`, and the alias lookups behind creating, moving and removing issues and Notes, now read issue and Note files through the same regular-file guard as the index: a node file that became a symlink, named pipe or device, or grew past 1 MiB, after the tree was walked is refused unread instead of followed or read in full. `check` reports it as a `not-regular` problem, and an edit or `fmt` fails with an error naming the file.
- `capcom rm`, `mv`, `know rm`, `know mv` and `agents` now read issue and Note files through the same regular-file guard: a node file that became a symlink, named pipe or device, or grew past 1 MiB, after the tree was walked is refused unread. Another node's refused file is left as it is and warned about like a file that does not parse, the Managed block leaves such a Note out, and the removed or moved node's own refused file fails the command with an error naming it.
- `rm`, `mv`, `know rm`, `know mv` and `--parent` on `create` and `know add` refuse an id or alias that two files claim, exiting 1 with an error naming both files relative to the repository, instead of resolving it to the first file.
- A command argument that is exactly the id or an alias of an issue or Note left out as a duplicate (`update`, `close`, `log`, `show`, `dep`, `related`, `know update`, ...) now exits 1 with an error naming the two clashing files, and one that is exactly the id of a file with problems is `not_found` naming that file. Before, both fell through to prefix matching, so `close foo` could close `foo-bar`.
- `capcom agents` and the automatic Managed-block refresh now write `AGENTS.md` durably (fsynced before and after the rename), keep a symlinked `AGENTS.md` a symlink by updating the file it points to, and keep the guide's file mode.
- `capcom mv` and `capcom know mv` with an empty or whitespace-only `--parent` now fail as a usage error (`--parent needs an id or "."`, exit 2) and move nothing. Before, `--parent ""` moved the issue or Note to the top of the tree; only `--parent .` does that now.
- `elsewhere.days` in `.capcom/config.yaml` now accepts 0 to 36500. A larger value used to overflow the Elsewhere scan's cutoff and silently turn the scan off; it is now a config error naming the file and line.
- A Note Ref that the disk cannot resolve — a symbolic-link loop, a name too long, or a file capcom may not read — is now reported by `capcom check` and `capcom know verify` as a broken Ref (`cannot be resolved: <reason>`), and the other Refs and Notes are still checked. Before, such a Ref aborted the whole command with an error.
- `go run ./cmd/release prepare vX.Y.Z` now fetches origin's `main` and its tags before checking the version, so a version origin has already released is refused (`vX.Y.Z is not above the highest release tag vX.Y.Z`) even when the local checkout lacks that tag. A failed fetch is a refusal too (`fetch origin's main and its tags: <reason>`), reported with the other refusals and writing nothing.
- When the index cannot commit a refresh, the error now names only the commit failure, without a trailing `sql: transaction has already been committed or rolled back`.
- `capcom lock break` now clears a lock record that is empty, unparsable or has no token, with a warning that it was discarded, instead of failing; `capcom lock status --all` and `capcom prime` skip such a record with a warning naming the file and still show every other worktree's lock.
- `capcom create` and `capcom know add` no longer overwrite a file that another session wrote at the same id a moment earlier: the second one now fails with `id "<id>" is already taken`, naming the file, and leaves that file as it was.
- Fixed: commands that edit an existing issue or Note (`update`, `close`, `know update` and the like) re-read the file just before writing it, with or without `--if-match`; when another writer changed it in the meantime they fail with the etag conflict and keep the newer file instead of overwriting it.

## [0.3.0] - 2026-10-12

- `capcom mv` now names a moved issue file that does not parse relative to the worktree root, as every other error does, and a failed rename in `capcom mv` or `capcom know mv` names the moved file and every path in its message relative to the worktree root.
- When `mv`, `know mv` or `rm` fails part-way and takes back the files it had already rewritten, each file now gets back its exact original bytes, CRLF line endings included, and its original file permissions. Before, a rolled-back file came back with LF line endings and mode 0644.
- `capcom lock touch` on a lock nobody holds now names the worktree in its result (`worktree: _main` or `wt-<name>`, with `lock: free`) instead of an empty one, and its `not_found` failure gives the lock record's file in the error's `path` field, with the message `no lock is held on this worktree`, the shape a `locked` failure already uses.
- An unknown key in an issue file now ends with the keys an issue knows (`unknown key "updated"; an issue has title, status, type, priority, labels, deps, related, plan, aliases, created, closed and reason`).
- Notes are now written with double quotes, like issues: a title or list entry that needs quoting (one holding `: `, for example) is written `title: "Fix: parser"` instead of `title: 'Fix: parser'`. A store whose Notes capcom wrote with single quotes fails `capcom fmt --check` after upgrading; run `capcom fmt` once to rewrite them, and `fmt --check` passes again.
- A `capcom rm` that fails part-way now also puts back the issue's empty children directory, not only the files whose deps or related entries it had already rewritten, and its error names every path relative to the working tree. `rm` now finds the issues that depend on the removed one by reading the issue files (the id plus its aliases, read from the file's raw frontmatter when it does not parse), as `mv` does; an issue file that does not parse is reported as `deps not checked` and no longer refuses the removal.
- `capcom mv` takes `--if-match <etag>`, as `know mv` does: it refuses with `conflict`, moving nothing, when the issue file changed since `show` printed its etag.
- A write command such as `create` no longer drops the `duplicate id` warning for an issue or Note file whose frontmatter also has a duplicate key: it now warns about both problems on that file.
- `capcom check`, `create`, `mv`, `know add`, `know mv` and `know rm` now word a directory problem the way the index warning does: a directory without its node file reads `directory without its node file: no <name>.md beside it; left out`, and the directory of a node file with an invalid id reads `directory left out: its node file <name>.md has an invalid id` (still code `orphan-directory` in `capcom check`).
- `capcom check` now words an alias that repeats its own file's id or is listed twice in that file the way the index warning does: `alias "<alias>" repeats the node's own id` and `alias "<alias>" is listed twice` (still code `duplicate`), instead of `duplicate alias "<alias>": the id of …` / `also an alias of …` naming the file itself.
- Ids for issues and Notes may now be a single word (`turn`, `driver`): an id is a kebab slug of one to four words, still at most 40 characters.
- Every command that takes an id, alias or prefix now accepts the way an id is cited in prose: the argument is trimmed, lowercased and each run of whitespace becomes one hyphen before it resolves, so `capcom know show "ADR 0076"` finds Note `adr-0076` and `capcom show "Login Timeout Race"` finds issue `login-timeout-race`. Dots and hyphens are kept as they are, and a not-found or ambiguous error still quotes the argument as typed.
- Knowledge Notes may carry two optional frontmatter keys: `retired: true` marks a Note that no longer holds, and `superseded-by: [ids]` names the Notes that replace it. `retired` accepts only `true` or `false` and is written only when true; a `superseded-by` entry must be spelled as an id, appear once and never name the Note itself. The canonical key order is now title, labels, refs, retired, superseded-by, aliases.
- capcom now reads store format 3, which adds the Note keys `retired` and `superseded-by`, and `capcom init` writes `format: 3`. Format 1 and 2 stores still load; a release that reads only format 2 refuses a format-3 store.
- `capcom know tree`, `capcom know search` and `capcom know show --with-children` now leave out a retired Note and everything below it; `--retired` brings them back. `capcom know show <id>` still shows a retired Note, with `retired: true` and `superseded-by: [ids]` lines, and `--json` Note data carries `retired` (only when true) and `superseded_by` (always, `[]` when empty).
- A retired top-level Note is left out of the AGENTS.md Managed block, and the refs of a retired Note and every Note below it are no longer checked by `capcom know verify`, `capcom check` or the Briefing's broken-ref count; `capcom check` still validates their frontmatter.
- `capcom check` reports a `superseded-by` entry that names no Note by id or by an alias (`missing-superseded-by`), and a Note using `retired` or `superseded-by` in a store declaring a format below 3, or without a `config.yaml` (`format-too-old`, at the key's line).
- `capcom know update` gains `--retire` / `--unretire` and `--add-superseded-by <id|alias|prefix>` / `--remove-superseded-by <id>` (both repeatable). A successor is stored by its canonical id; one naming no Note is refused `not_found` and one naming the Note itself `invalid`, both at the Note file, and `--retire` with `--unretire` is a usage error. The first write that retires a Note or adds a successor in a store below format 3 raises `.capcom/config.yaml` to format 3 with a warning, as `related add` does for format 2.
- `capcom know mv` now rewrites every other Note's `superseded-by` entry naming the renamed Note (by its id or one of its aliases) to the new id, and `capcom know rm` drops the removed Note from every `superseded-by` list naming it; a write that fails part-way takes back every file. A Note file that does not parse is skipped with the warning `<path>: superseded-by not checked for <id>: the file does not parse` and fails neither command.
- Notes may now be edited by hand; `capcom check` and `capcom fmt --check` validate the result. `docs/format.md` documents the `retired` and `superseded-by` Note keys, `--retired`, and the `missing-superseded-by` and `format-too-old` check codes, and the README shows glossary and decision records as Note trees.

## [0.2.0] - 2026-10-12

- `config.yaml` accepts a `format:` key, the store format version (a missing key means 1). A store whose format is newer than the binary reads makes every command fail with `.capcom/config.yaml:<line>: store format <n> is newer than this capcom reads (up to <max>); upgrade capcom`; `capcom prime` reports it as one `warning: store:` line and still exits 0.
- `create` and `mv` no longer fail because some other file in the issue tree has a bad name, sits in a directory without its node file, or repeats an id or alias. They fail only when the problem concerns the issue being written or moved, its new path or the parent they resolve; every other problem is reported once as a warning after the result.
- `know add`, `know mv` and `know rm` no longer fail because some other file in the Knowledge tree has a bad name, sits in a directory without its Note file, or repeats an id or alias. They fail only when the problem concerns the Note being written, moved or removed, its new path or its parent; every other problem is reported once as a warning after the result.
- `capcom check` reports git conflict markers left in an issue or Note file by a merge (code `conflict`, at each marker's line), and `docs/format.md` describes how to resolve a conflict in an issue's Log.
- `--kv` is now a flag of the commands that print `KEY=VALUE` records (`show`, `close`, `reopen`, every `lock` subcommand, `version`, `create`, `update`, `log`, `mv`, `dep add` and `dep rm`) and appears only in their help. It no longer shows in `capcom --help`, and any other command rejects it as an unknown flag (exit 2). `--kv` must now follow the command name: `capcom --kv version` is a usage error; write `capcom version --kv`.
- Elsewhere (the report of unmerged issue changes in `ready`, `list`, `show` and `prime`) now scans remote-tracking branches (`refs/remotes/`) as well as local branches, and names them by their short name, e.g. `login-flow: done on origin/fix-login (unmerged)`. It skips the current branch's remote-tracking upstream and the `origin/HEAD` pointer. When a local branch and a remote-tracking branch with the same name hold the same work, it reports them once: as the local branch when the remote is level or behind it, and as the remote when the local branch is behind. capcom still never fetches, so a remote-tracking branch is only as fresh as the last `git fetch`; the `elsewhere.days` window applies to remote-tracking branches too.
- `capcom fmt` rewrites every issue and Note file that is not in canonical form, so a hand-written file no longer churns on its first capcom edit. Files that do not parse or validate are left untouched and reported as warnings. `capcom fmt --check` writes nothing, lists the files that would change and exits 1 when any would.
- `capcom init --codex-hooks` adds `capcom prime` hooks to `.codex/hooks.json` (SessionStart and PreCompact), creating the file when missing and keeping every existing hook, so Codex sessions start with a briefing. A re-run changes nothing; `--json` reports `codex_hooks` as `added` or `present`. Codex runs hooks only with `[features] hooks = true` in its `config.toml`.
- The beads migration guide now covers `bd remember` memories, what does not migrate, dated `notes`, non-plan `spec_id`s, `parked` lowering ready counts, two-sided `related` links, dotted ids, replacing beads' Claude Code and Codex hooks, `capcom fmt`, `conflict` problems and `git config --local` for `core.hooksPath`.
- `create`, `mv`, `know add`, `know mv` and `know rm` no longer hide a tree problem (an invalid id or alias, a duplicate id or alias, a directory without its node file) on a file the index refresh already warned about for a different reason, such as an unknown status. A tree problem is left out only when an index warning names the same file and the same kind of problem, so each problem is reported once.
- `mv` and `know mv` now name a bad file inside the moved node's children directory by its path after the move, reported once, instead of by the path it had before the move.
- The Managed block that `capcom agents` writes into `AGENTS.md` now points an agent without a `capcom` binary at capcom's source and install instructions (https://github.com/airiclenz/capcom#install). An existing block reads as out of date after upgrading: run `capcom agents` once to refresh it (`capcom check` and `capcom agents --check` report it until you do).
- `capcom rm <id|alias|prefix>` deletes an issue file together with its aliases, and its parent's directory when that empties. It refuses (code `invalid`, naming the file, changing nothing) an issue with children, an issue whose children directory still holds any file, and an issue other issues depend on, listing them by id; `--drop-deps` removes those `deps` entries instead (also when they name an alias). `--if-match <etag>` refuses a stale etag with a conflict. `--json` reports kind `issue-remove` with `id`, `path` and `deps_dropped`; `--kv` prints `ID`, `PATH` and `DEPS_DROPPED`. A file of another issue that does not parse is warned about as `deps not checked`.
- `capcom merge-driver <base> <ours> <theirs> <path> [<base-label> <ours-label> <theirs-label>]` is a git merge driver for issue files (git's `%O %A %B %P %S %X %Y`). It merges the `## Log` section by entry, so two branches that each append Log entries merge cleanly, and merges the rest of the file with `git merge-file`. The result replaces `<ours>` byte for byte (CRLF stays CRLF). It exits 0 when the merge is clean, and 1 with `<path>: conflict markers remain; resolve them and stage the file` when markers remain. Conflict markers carry the given labels, or `<path> (ours)`, `<path> (base)` and `<path> (theirs)` when the labels are absent or arrive unexpanded (git before 2.44). It works outside a capcom store.
- `capcom init --merge-driver` adds `.capcom/issues/**/*.md merge=capcom-log` to `.gitattributes` and prints the two `git config` commands that define the `capcom-log` driver. Once they are run, git merges an issue's Log by entry, so two branches that each log on the same issue merge without a conflict. capcom never writes `.git/config`. Without the config, git merges as usual.
- The store format is now 2: issue files may carry a `related: [<id>, ...]` key, written after `deps`, and `capcom init` writes a real `format: 2` line into `config.yaml` instead of the `# format: 1` comment. A `config.yaml` without a `format:` key still reads as format 1, and a store of format 3 or above is refused as too new.
- `capcom check` reports a related link that names no issue (`missing-related`) or names the issue itself (`field`), at the `related:` line.
- `capcom related add <a> <b>` links two issues without making either depend on the other, and `capcom related rm <a> <b>` removes the link from whichever issue holds it. `capcom show` lists an issue's related links in text and `--json`, both the ones its own file holds and the ones other issues hold to it. The first link written in an older store raises `.capcom/config.yaml` to store format 2 and prints a warning, because capcom releases that read only format 1 cannot read that store any more.
- A renaming `capcom mv` now rewrites other issues' `related` entries that name the old id or one of its aliases, as it does `deps`. `capcom rm` drops other issues' `related` entries naming the removed issue without refusing, and reports those issues as `related_dropped` (text, `--json` and `--kv` as `RELATED_DROPPED`).
- `docs/format.md` documents the `related` key, `capcom related add` and `rm`, how `show`, `mv`, `rm` and `check` treat related links, store format 2 and how the first link raises it; the README lists the `related` commands, and the beads migration guide maps beads `related` links to `capcom related add` instead of Log entries.

### Fixed

- Tree problems printed by `check`, `create`, `mv`, `know add`, `know mv` and `know rm` (an invalid id or alias, a duplicate id or alias, a directory without its node file) now name every file relative to the worktree root, including the other file of a duplicate, instead of as an absolute path. `check` cites the line of the `aliases` key for a duplicate or invalid alias instead of line 0.

## [0.1.0] - 2026-10-11

### Added

- `capcom` binary with a `version` command and three output modes: plain text, a versioned `--json` envelope (`{schema, kind, data, elsewhere, warnings}` or `{schema, kind: "error", error: {code, message}}`) and `--kv` `KEY=VALUE` lines ending in `STATUS=`. Exit codes: 0 ok, 1 error, 2 usage, 3 not found or locked.
- `capcom init` creates the store in the current git repository: `.capcom/config.yaml` with the default configuration (statuses `open`=todo, `active`=doing, `parked`=waiting, `done`=done, `dropped`=dropped; types `bug, feature, task, chore`; plan dirs `docs/plans`, `docs/plans/archived`; lock TTL 2h; Elsewhere window 30 days), `.capcom/issues/` and `.capcom/knowledge/`. Re-running it changes nothing, and it works from any subdirectory. Outside a git repository it fails with `invalid`; an invalid `config.yaml` (unknown key, unknown status category, no `todo` or `done` status) fails with `path:line`.
- Issue files: markdown with a YAML frontmatter (`title, status, type, priority, labels, deps, plan, aliases, created, closed, reason`), written in one canonical form that round-trips byte for byte; unknown keys and bad values are reported as `path:line` errors. `docs/format.md` documents issue files, the tree and `config.yaml`.
- A disposable SQLite index at `<git-dir>/capcom/index.db` mirrors the issue tree: it refreshes incrementally (size + mtime, racy-clean safe), rebuilds itself when the schema or the configured statuses/types change, and supports full-text search over titles and bodies. A bad issue file, or two files claiming the same id or alias, is left out and reported as a `path:line` warning while everything else keeps working. New `capcom reindex` rebuilds the index from scratch.
- New `capcom list`: every issue that is not closed, in tree order with children indented, one `id  status  P<n>  title` line each; filters `--status`, `--category`, `--label` (all required), `--no-label`, `--type`, `--priority`, `--parent`, `--plan <substring>`, `--planned`/`--unplanned`, `--all` and `--limit`.
- New `capcom show <id|alias|prefix>...` prints each issue in full (its fields as `key: value` lines, then the body verbatim); `--kv` prints `ID= ISSUE_STATUS= CATEGORY= TITLE=` and a per-id `STATUS=ok|not_found`, and a missing id exits 3 while the issues found are still printed. Each issue's etag is shown as an `etag:` line after `path:` in text, `ETAG=` in `--kv` and `etag` in the `--json` issue data.
- New `capcom search <words>` finds issues whose title or body holds every word, best match first; no match is `not_found`.
- New `capcom ready`: the issues ready to work on (status in the `todo` category, every dep `done` or `dropped`, no open child, no `waiting` or `dropped` ancestor), most urgent first and in tree order within a priority, one `id  status  P<n>  title` line each. A dep resolves by exact id, then alias (never prefix); one naming nothing blocks as `missing`, and one satisfied only because it was dropped is reported as a warning. Issues carrying a `ready.hide` label are left out unless `--show-hidden`; filters `--label` (all required), `--no-label`, `--planned`/`--unplanned` and `--limit`. `--all` also lists the todo issues that are not ready with what keeps them back; in `--json` each entry carries `ready`, and `blocking` (`{dep, reason}`), `open_children` and `held_by` when they apply.
- New `capcom create --id <slug> --title <t>` with `--parent`, `--type` (default `task`, or the first configured type), `--priority`, `--label` (repeatable or comma-separated), `--plan`, `--status` (default: the first `todo` status) and `--body-file <path|->`. The id is always the caller's: an invalid slug is refused `invalid`, an id that is already an issue's id or alias is refused `exists`, and a child goes into its parent's directory. A closed status is refused (create open, then close).
- New `capcom update <id>`: `--title`, `--status`, `--type`, `--priority`, `--plan` (empty clears it), `--add-label`/`--remove-label`, `--body-append <text>` (literal) or `--body-append-file <path|->`, and `--body-replace-old <s> --body-replace-new <s>` (the old text must occur exactly once). `--if-match <etag>` refuses with `conflict` when the file changed since it was shown. A status change into or out of a closed category is refused; `close` and `reopen` own those moves.
- New `capcom log <id> <text>`: appends `- YYYY-MM-DD <author>: <text>` under the issue's `## Log` section, creating the section when missing. The author is `$GIT_AUTHOR_NAME`, else `git config user.name`, else `$USER`.
- `create`, `update` and `log` re-validate the issue, write it atomically and print its id, path and new etag (`id:`/`path:`/`etag:` lines; `ID`/`PATH`/`ETAG` in `--kv`; kind `issue-write` in `--json`).
- New `capcom close <id>... --reason <text> [--status <s>]`: moves each issue to a status in the done or dropped category (default: the first done status in config), records `closed` (now, UTC) and `reason`. Each id is handled on its own: an issue already closed is left alone and reported `already_closed`, an unknown id does not stop the others but the command exits `not_found` (3). `--kv` prints `ID=` and `STATUS=closed|already_closed|not_found` per id. A missing `--reason` is a usage error, a blank one `invalid`.
- New `capcom reopen <id> --reason <text> [--status <s>]`: moves a closed issue back to the first todo status (or a todo/doing/waiting status given with `--status`), clears `closed` and `reason`, and appends `reopened: <reason>` to its Log. Reopening an issue that is not closed is refused `invalid`.
- New `capcom dep add <id> <dep-id>`, `capcom dep rm <id> <dep-id>` and `capcom dep list <id>`. Ids, aliases and prefixes are accepted; an edge is stored under the canonical id of the issue depended on. `dep add` refuses a self-dependency and any edge that would create a cycle (`invalid`, naming the cycle, e.g. `a -> b -> c -> a`); `dep rm` removes a dep whether the file writes it as an id or an alias (a dep naming no issue is removed by its exact text) and fails `not_found` when there is none; `dep list` prints the deps (unresolvable ones marked `missing`) and the issues that depend on it.
- New `capcom mv <id> [<new-id>] [--parent <id|.>]` renames an issue and/or moves it with its subtree below another issue or to the top of the tree. A rename keeps the old id as an alias and rewrites every dependency that named the issue; a move below the issue's own descendants, or onto an id or alias another issue holds, is refused. Files move by plain rename (never `git mv`), and a failed move rolls back every change it made.
- Knowledge Notes: markdown files under `.capcom/knowledge/` with a YAML frontmatter of `title, labels, refs, aliases` and a free body, nested by directory like issues. The index now holds Notes too (full text over title and body, labels); an issue and a Note may share an id, and `capcom search` still finds issues only. The index schema version is bumped, so an existing index rebuilds itself once.
- New `capcom know tree [id] [--depth N]` prints the outline of Note ids and titles, children indented two spaces; `--depth` limits the levels printed below the top (or below the named Note).
- New `capcom know show <id|alias|prefix> [--with-children]` prints a Note in full (`key: value` lines, then the body), and with `--with-children` the Notes directly below it.
- New `capcom know search <words> [--label <l>]` finds Notes holding every word (and every label), best match first; no match is `not_found`.
- New `capcom know add --id <slug> --title <t> [--parent <id>] [--label <l>] [--ref <path|path#symbol>]... [--body-file <path|->]` writes a Note with a chosen id; a taken id or alias is refused `exists`, and a ref outside the working tree is refused `invalid`.
- New `capcom know verify` lists every Note ref that no longer resolves (a missing path, a `path#symbol` whose file lacks the symbol text, a path outside the working tree) as `path:line: ref "<ref>": <reason>`, citing the ref's line in the Note, and then exits 1; with every ref resolving it prints nothing and exits 0.

A lock is stale once its heartbeat is older than `lock.ttl` (2h by default). Every lock command supports `--kv`: `LOCK=acquired|resumed|held|free|released|stale`, `HOLDER=`, `PURPOSE=`, `SINCE=`, `HEARTBEAT=`, `TOKEN=` (only ever the caller's own), then `STATUS=`; `status --all` leads each record with `WORKTREE=`.
- `capcom ready`, `list` and `show` now report, apart from their result, the issue files changed on other local branches (including branches checked out in other worktrees) that HEAD has not merged: one `elsewhere: <id>: <status> on <branch> (unmerged)` line each in text (`added` or `removed` for a new or deleted file, `modified` when the branch copy does not parse), and `{id, branch, change, status, path}` objects in the `--json` envelope's `elsewhere` member. Only branches whose tip is newer than `elsewhere.days` (default 30; 0 scans none) and that hold commits HEAD lacks are compared, against their merge base; a rename shows as `removed` + `added`, and `show` reports only the shown issues. Nothing is fetched or merged; a git failure, an unborn HEAD or an unparsable branch copy becomes a warning and the result still prints. `--no-elsewhere` skips the scan, and `--kv` leaves it out. Uncommitted changes in other worktrees are not scanned.

It prints one `path:line: message` per problem and exits 1 when there are any; `--json` returns `kind: check` with a `[{path, line, code, message}]` list.
- New `capcom prime` prints the session Briefing: Ready work split into planned and unplanned (15 shown per list, with the full count), issues in a `doing` status, the Tree lock of every worktree with holder, age, heartbeat age and a `(stale)` flag, issue changes on other branches (Elsewhere), broken Note refs and the number of `capcom check` problems. It never fails a session: a broken config, a missing store or an unreadable index becomes one `warning:` line and the command still exits 0. `--json` returns `kind: prime` with `ready_planned`, `ready_unplanned` (`{count, issues}`), `doing`, `locks`, `broken_refs` and `check_problems`; a section whose source failed is left out.
- New `capcom agents` writes or refreshes the capcom Managed block of `AGENTS.md`, between `<!-- BEGIN CAPCOM -->` and `<!-- END CAPCOM -->`: capcom as the issue register of record, the core commands and the top level of the Knowledge tree. It appends the block when absent (creating `AGENTS.md` when missing), never touches a byte outside the markers and keeps a CRLF file CRLF. `capcom agents --check` exits 1 at `AGENTS.md:<line>` when the block is out of date; an `AGENTS.md` without the block, or none at all, is fine. Tangled markers are reported `invalid` at their line.
- `capcom check` also reports an out-of-date Managed block (code `agents-block`, at the begin marker's line), and a top-level `capcom know add` refreshes an existing block in the same command, so `check` stays green.
- `capcom init --claude-hooks` adds SessionStart (`startup|resume|clear|compact`) and PreCompact hooks running `capcom prime` to `.claude/settings.json`, creating it when missing. Only the `hooks` member is rewritten: every other key keeps its place and its values their bytes (`&&`, `<`, `>` and numbers included), and a re-run changes nothing. Plain `capcom init` prints that hooks snippet in text mode (not in `--json`).
- `docs/format.md` now also documents Note files and Refs, the Tree lock record and the Managed block of `AGENTS.md` (including that a top-level `know add` refreshes an existing block); new `docs/migrating-from-beads.md` gives the beads-to-capcom field mapping and the migration steps; the README describes the shipped commands. capcom now tracks its own work in `.capcom/` and carries the Managed block in its `AGENTS.md`.

It skips every step already done, so rerunning it resumes a half-finished release.
- A push to `main` that changes VERSION to a bare `X.Y.Z` now creates the annotated release tag `vX.Y.Z` on that commit (an existing tag is left alone), and CI cross-builds `capcom` for Linux, macOS and Windows on amd64 and arm64.

It is read-only and never publishes.

- `capcom know show` prints each Note's etag as an `etag:` line after `path:` in text and an `etag` field in the `--json` Note data, computed from the Note file on disk; `capcom know add` prints the new file's etag (`etag:` line, `etag` in `--json`).
- New `capcom know update <id|alias|prefix>` changes a Note: `--title`, `--add-label`/`--remove-label`, `--add-ref`/`--remove-ref` (a new ref outside the working tree is refused `invalid`), `--body-file <path|->` to replace the whole body, or `--body-append <text>`, `--body-append-file <path|->` and `--body-replace-old <s> --body-replace-new <s>` (the old text must occur exactly once). `--if-match <etag>` refuses with `conflict` when the file changed since `know show` printed it. It prints the Note's `id:`, `path:` and new `etag:`, and refreshes an existing AGENTS.md capcom block when the top level changed (`refreshed: AGENTS.md`); tangled block markers are a warning, not a failure.
- New `capcom know mv <id|alias|prefix> [<new-id>] [--parent <id|alias|prefix|.>]` renames a Note, moves it below another Note (`.` is the top level), or both; its children move with it. A rename keeps the old id as an alias, so `know show <old-id>` still finds the Note. A new id another Note holds as its id or alias is refused `exists`, and a move below the Note's own subtree `invalid`. `--if-match <etag>` refuses with `conflict` when the file changed since `know show` printed it. It prints the Note's `id:`, `path:` and `etag:`, and refreshes an existing AGENTS.md capcom block when the top level changed (`refreshed: AGENTS.md`); tangled block markers are a warning, not a failure.
- New `capcom know rm <id|alias|prefix> [--if-match <etag>]` deletes a Note file and prints its `id:` and `path:`; its aliases go with it, so those ids are free again. A Note with children is refused `invalid`, naming the Note file and how many child Notes it has, and so is a Note whose children directory still holds other files; nothing is deleted. An empty children directory of the Note, and its parent's children directory when the removal empties it, are removed with it. `--if-match <etag>` refuses with `conflict` when the file changed since `know show` printed it. An existing AGENTS.md capcom block is refreshed when the top level changed (`refreshed: AGENTS.md`); tangled block markers are a warning, not a failure.

### Fixed

- An issue whose title, reason, label or other frontmatter text holds a rune outside YAML's printable set (U+FFFE, U+FFFF) is now written escaped, so the file parses back instead of failing with `control characters are not allowed`.
- `capcom know verify` and `capcom check` list a Ref whose path runs below a file (`README.md/sub`) as a broken Ref with `no such file or directory`, instead of aborting with `not a directory` before printing any other finding.
- An empty entry in a label list (`--label "x,,y"` on `create` and `know add`, `--add-label "x,,y"` on `update` and `know update`) is dropped instead of being written as `""`, which left an issue or Note file that no longer parsed.
