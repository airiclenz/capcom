---
title: "ADR 0016 amendment of 2026-10-26: a resume under a new purpose moves the token file, and finish --keep-lock names the token for the next start"
---

Amended 2026-10-26: one token now has one token file. The decision wrote a token file for every
purpose a lock was taken or resumed under and never removed the others, so after
`capcom lock acquire --purpose alpha` and a resume of the same token as `beta`, a session naming
`alpha` still resumed the lock. The decision's own promise, that a session naming any other purpose
fails `locked`, held only until a token was reused under a second purpose.

**A resume under a new purpose moves the token file.** An acquire or start that resumes the lock
with `--token` under a purpose other than the one its token file holds writes the token file for
the new purpose and deletes every other token file of this worktree holding the same token, in the
same guarded step. The lock's purpose becomes the new one. A session naming the old purpose then
fails `locked` with exit code 3, as a session naming any other purpose does.

**`finish --keep-lock` names the token for the next start.** `--keep-lock` keeps the lock under the
finished Issue's purpose and its token file, and prints the token. Its `next:` line names the start
that carries the lock on, `capcom start <next-id> --token <token>`, so the one command it
recommends is the one that works; that start moves the token file to the next Issue's id as above.
A start without `--token` for an Issue other than the kept purpose still fails `locked`: capcom
never writes a token file for a purpose the session has not named, so the lock keeps telling
different work apart.

Rejected with it: writing a token file for the `next:` Issue at `finish --keep-lock`, so that a bare
`capcom start <next-id>` resumes. It widens the purpose boundary to an Issue the session has not
claimed, and it fails whenever the agent picks another Ready Issue than the one `next:` named.
